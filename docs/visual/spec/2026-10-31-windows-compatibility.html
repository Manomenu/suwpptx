Suwpptx Studio spec Spec

TL;DR

Someone who doesn't code, on Windows or Fedora, tells Claude Code "install Manomenu/suwpptx", and that one request sets up the whole studio:

  • the folder ~/suwpptx,
  • the suwpptx plugin, switched on only in that folder,
  • the app as one ready-made program,
  • a "Suwpptx Studio" shortcut.

From then on, opening the shortcut, or starting claude in ~/suwpptx, starts the app by itself. Claude Code sessions in any other folder don't see the plugin.

Development stays on Fedora with the current gate. Windows only has to run the app, not build it.

Problem

Today, running Suwpptx Studio means cloning the repository and using the developer setup: .NET 10 SDK, Node and pnpm, just, then just server and just web in two terminals, and installing the plugin from the repository root. That is fine for the owner on Fedora and impossible for someone who doesn't code. On Windows it would not even work. Reading the code shows these breakages:

WhereWhat goes wrong
Suwpptx.Server/Previews/SlideRenderer.cs:112The server looks for a file named exactly soffice on PATH. On Windows it is soffice.exe, and LibreOffice's installer doesn't add it to PATH, so no previews are ever drawn.
the same file, pdftoppmPoppler is one more tool to install, and on Windows there is no simple way for a non-coder to get it.
plugin/skills/*/SKILL.mdThe skills call python3, which on Windows is usually missing or is the Microsoft Store placeholder.
Suwpptx.Server/Folder/FolderNames.csNames that Windows reserves (CON, nul.txt, notes.) are accepted, so on Windows they fail with a server error.
the app itselfIt is two processes (the API, and the web UI served by vite or nginx). There is no downloadable build.

Goals and non-goals

Goals

  • One request to Claude Code ("install Manomenu/suwpptx") installs everything, on Windows and on Fedora
  • The plugin is on only in ~/suwpptx: no hook and no skills in sessions elsewhere
  • The app is one downloadable program per OS that serves the UI and the API. It needs no .NET, Node or nginx
  • Previews need only LibreOffice
  • Starting Claude Code in ~/suwpptx starts the app when it isn't running
  • A "Suwpptx Studio" shortcut opens a terminal in ~/suwpptx with Claude Code
  • Asking again ("update suwpptx") updates the plugin and the app

Non-goals

  • Developing on Windows: the gate, just and the scripts stay Fedora-only
  • Installing Claude Code itself and Git for Windows: the user has them, since the request is made in Claude Code
  • Installing LibreOffice or Python without asking: Claude asks first, then runs the command
  • macOS, a signed installer, a Windows service, auto-update in the background
  • The container stack for users: it stays a developer tool

Scenarios

1. Ola installs it on Windows (main path)

  1. Ola has Claude Code. She types: "install Manomenu/suwpptx".

  2. Claude reads the repository's install instructions and runs the install script. The script:

    • creates C:\Users\ola\suwpptx,
    • installs the plugin there at project scope,
    • downloads suwpptx-win-x64.zip from the latest release into the plugin's data folder,
    • adds a "Suwpptx Studio" shortcut to the desktop.

  3. The script reports that LibreOffice and Python with python-pptx are missing, and gives the winget and pip commands. Claude asks "May I install LibreOffice and Python?", Ola says yes, and Claude runs them.

  4. Claude says: "Done. Open Suwpptx Studio from your desktop."

  5. Ola double-clicks the shortcut. Claude Code opens in ~/suwpptx, and the plugin's start hook launches the app and opens http://localhost:6310 in her browser.

  6. She types "/suwpptx:make q3".

2. A session somewhere else

  1. Ola opens Claude Code in her own project folder. The plugin isn't active: no hook runs, no suwpptx skills in the list, and nothing is started.

3. Updating

  1. "update suwpptx" in ~/suwpptx. Claude runs the same script again. It updates the plugin, downloads the newer app, restarts it, and leaves workspaces and templates untouched.

4. The owner on Fedora

  1. Same request, same script. LibreOffice comes from dnf, and the shortcut goes into the application menu. In the development repository nothing changes: just server/just web and the repository's own project-scoped plugin.

Behaviour

The folder is the switch. The plugin is installed at project scope for ~/suwpptx: ~/suwpptx/.claude/settings.json enables suwpptx@suwpptx, and the marketplace is registered for the user. A session started in ~/suwpptx gets the skills and the start hook. Every other session gets nothing. The app never lists .claude/, because names starting with a dot are its own.

Installing is a script, not something Claude improvises. The repository has an "Install with Claude Code" section that Claude follows. It downloads and runs install.sh from the repository in bash, which on Windows is Git Bash: Claude Code requires Git for Windows there. One script for both systems, so it can be tested. The start hook only starts the app or says what is missing; it never downloads or installs.

The app is one program. A self-contained .NET publish per OS (win-x64, linux-x64) holds the server and the built web UI. It serves both on http://localhost:6310. Previews come from LibreOffice to PDF, and the app turns PDF pages into PNG itself, so poppler is no longer needed. Releases are built by CI when a version tag is pushed.

Rules and edge cases

SituationExpected behaviour
LibreOffice installed, not on PATH (normal on Windows)The app also looks in the standard install folders: %ProgramFiles%\LibreOffice\program, the x86 one, and /usr/bin, /usr/lib/libreoffice/program on Fedora.
LibreOffice or Python missing when installinginstall.sh finishes everything else and ends with a list of what is missing, with the exact command for this OS (winget on Windows, dnf on Fedora, pip install --user python-pptx). Its exit code says "needs these".
Running the install againIt does nothing that is already done. It updates the plugin and the app to the newest release, stops a running older app, starts the new one, and never touches workspaces or templates.
Port 6310 taken by another programThe hook says "port 6310 is used by another program" and doesn't start a second app.
Session started in a subfolder (~/suwpptx/workspaces/q3)Not supported. The shortcut always starts in ~/suwpptx, and the docs say so.
No network while installingThe script stops with "can't reach github.com" before changing anything.
Python on WindowsThe skills use the first of python3, python and py -3 that can import pptx; the Store placeholder fails and is skipped.
Names Windows reserves (CON, NUL, COM1…, with or without an extension, a trailing dot or space)Refused with 422 on every OS, saying to pick another name.
Two workspace names differing only in caseRefused with 409 on every OS: Windows sees one folder.

Acceptance criteria

  • AC-windows-compatibility-1 A pushed version tag makes CI publish a release with suwpptx-win-x64.zip and suwpptx-linux-x64.zip, each holding one self-contained executable
  • AC-windows-compatibility-2 The executable alone, with no .NET, Node or nginx installed, serves the web UI at / and the API at /api on http://localhost:6310
  • AC-windows-compatibility-3 Previews render with only LibreOffice installed (no pdftoppm on the machine), and the app finds LibreOffice on PATH (with PATHEXT on Windows) or in its standard install folder
  • AC-windows-compatibility-4 install.sh run in a fresh home creates ~/suwpptx with .claude/settings.json enabling suwpptx@suwpptx, puts the app for this OS into the plugin's data folder, creates the shortcut, and lists each missing tool with its install command
  • AC-windows-compatibility-5 Running install.sh a second time changes nothing that is current, upgrades an older app, and leaves every file under workspaces/ and templates/ as it was
  • AC-windows-compatibility-6 The start hook starts the app and opens the browser when the app is installed and not answering; prints one line pointing to the install when it isn't installed; does nothing when the app answers; and returns within 2 seconds in every case
  • AC-windows-compatibility-7 A Claude Code session started outside ~/suwpptx on a machine set up by install.sh has no suwpptx skills and runs no suwpptx hook
  • AC-windows-compatibility-8 The skills that run Python find it as python3, python or py -3, whichever imports pptx
  • AC-windows-compatibility-9 A workspace or file name that Windows reserves is refused with 422, and a workspace name differing only in letter case from an existing one with 409, on every OS
  • AC-windows-compatibility-10 A CI job on a Windows runner installs the built win-x64 app with install.sh in Git Bash, starts it, and renders a three-slide deck into three PNGs

Risks and assumptions

"install Manomenu/suwpptx" depends on Claude finding the instructions. Claude Code has no built-in "install a repository" command, so Claude will look the repository up. The README gets an "Install with Claude Code" section at the top, short and imperative, with the one command to run. It still depends on the model reading it; the docs also give the command for a human to paste.

An unsigned program downloaded by a script. Files fetched with curl carry no "downloaded from the internet" mark, so SmartScreen usually stays quiet, but antivirus may scan or hold the file the first time. Code signing is left for later.

Running a script from the internet. install.sh comes from the repository's master branch over HTTPS. Anyone who can push to master can change what users run. That is acceptable for one owner; pinning the script to a release tag is the stricter option.

Release size. A self-contained .NET app with the web UI is roughly 70–100 MB per OS. LibreOffice is still a separate install, of about 350 MB.

Claude Code on Windows runs Bash-tool commands and plugin hooks in Git Bash, which it requires. The start hook and install.sh are bash, so they behave the same on both systems.

Project-scoped plugins load when the session starts in the folder whose .claude/settings.json enables them. Whether they also load in a subfolder was not checked, which is why the shortcut always starts in ~/suwpptx.
