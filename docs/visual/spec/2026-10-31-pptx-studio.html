Suwpptx Studio

Spec

TL;DR

Suwpptx Studio is a local app for building PowerPoint decks with Claude Code. Everything lives in one folder on disk. Each workspace is a subfolder holding a context.md with the requirements, any files you like (photos, videos, code, notes, older decks) and the deck's versions. A shared templates/ folder holds decks whose look gets reused.

Claude Code works directly on those files. The suwpptx plugin gives it the skills /suwpptx:make, /suwpptx:brief and /suwpptx:template, and Claude builds each .pptx itself. The web app shows the folder nicely: it lets you drop files in, draws slide previews, and gives most of the screen to the newest deck, with a Download .pptx button. There is no MCP server, no API for the agent and no database.

Problem

What the repo has today: the template's example feature Notes/ on PostgreSQL (server and web) and nothing about presentations. Making a deck with Claude means:

Today

  • pointing Claude at photos, an old company deck and the requirements again in every session
  • generated .pptx files pile up wherever the session happened to write them
  • you can't see the slides until you open each file in PowerPoint
  • "use our corporate look" means Claude guesses colours and fonts from a description
  • requirements collected over a week of sessions are scattered across them

With Suwpptx Studio

  • they sit in the workspace folder, and every session finds them there
  • every build is a numbered version in the workspace's versions/
  • the app shows the slides as soon as a version appears
  • a template .pptx is a file; Claude reads its theme, fonts and layouts from it
  • context.md in the workspace collects them, and Claude appends to it

Goals and non-goals

Goals

  • One root folder (default ~/suwpptx) is the single source of truth
  • Workspaces: browse, create, rename, delete in the app; the same by plain folder operations
  • Loose resources of any file type: drop in, view nicely, download, delete
  • A shared template library with slide previews
  • A viewer for the deck that takes most of the screen, with versions and a Download .pptx button
  • Anything that changes in the folder from outside (Claude, a file manager) shows up in the open app by itself
  • A suwpptx Claude Code plugin with the make, brief and template skills
  • A calm, pleasant look (shadcn + Tailwind, light and dark)

Non-goals

  • An MCP server or an API for agents. Claude Code uses the files
  • Claude Desktop and claude.ai chat: they can't see the owner's disk. An MCP layer over the same folder can come later if needed
  • A database. A workspace is a folder, a resource is a file, a version is a file
  • Building, changing or reading the style of .pptx files on the server. Claude does that
  • Editing slides or text files in the browser, and a chat box inside the app
  • A "select template" control. Claude picks the template from context.md or the conversation
  • Several users, accounts, sharing; any access from another machine
  • Thumbnails, sorting options or archiving on the workspace list

Scenarios

1. Owner builds a quarterly deck (main path)

  1. In the app the owner creates the workspace q3-board-review and drops in sales-q3.xlsx, six product photos and demo.mp4. The company deck acme-2025.pptx goes into Templates. On disk this is ~/suwpptx/workspaces/q3-board-review/.

  2. In Claude Code: "/suwpptx:brief q3-board-review: 12 slides max, revenue first, use the acme look". Claude writes this into the workspace's context.md, and the app shows the change.

  3. "/suwpptx:make q3-board-review". Claude reads context.md, the spreadsheet, the photos and templates/acme-2025.pptx. It builds the deck on top of the acme slide masters and saves versions/v1.pptx. The app renders previews, and v1 appears in the open viewer.

  4. Claude looks at the preview images of v1, sees that slide 4 overflows, and saves v2.

  5. The owner flips through v2 and clicks Download .pptx. PowerPoint opens it with the acme fonts and colours.

2. Owner iterates with a photo from elsewhere on disk

  1. "in q3-board-review swap slide 6's photo for ~/Pictures/team-2026.jpg and make the title shorter".

  2. Claude copies the photo into the workspace's resources/, changes slide 6 in a copy of v2 and saves v3. Both the new photo and v3 show up in the app without a reload.

3. Starting a new deck from an old one

  1. The owner creates hiring-pitch with only a notes.txt and says: "make it like the q3-board-review deck". Claude uses workspaces/q3-board-review/versions/v3.pptx as the style source.

4. Cleaning up without the app

  1. "delete the test-1 workspace and the old conference template". Claude removes both from disk. The open app drops them from its lists within seconds.

Behaviour

The folder is the source of truth; there is no database and no agent API. The app and Claude Code run on the same machine. Everything the owner might ask Claude to do (add, rename, delete, edit context.md, build a deck) is a plain file operation Claude Code already has. The server reads the folder, writes what the owner does in the UI into it, renders previews, and pushes changes to the open browser.

Claude builds the .pptx; the server never does. A deck cut to the requirements needs Claude's judgement, not a fixed slide engine. Claude builds it with its own tooling (Python and python-pptx) on top of the template file, and saves it as the next version.

Three skills, in a Claude Code plugin. make builds or rebuilds the deck from the workspace and the conversation, then checks the preview images. brief writes what was said into context.md. template describes a deck's look and layouts (theme colours, fonts, slide masters, placeholders) so that make reuses them. Plain actions ("copy this photo in", "delete demo.mp4") need no skill. The skills know the folder layout below and find the root folder from SUWPPTX_ROOT, or ~/suwpptx when it is not set.

A template is a file, not a setting. Any .pptx or .potx in templates/, in a workspace's resources/ or in another workspace's versions/ can be a style source. Claude picks one from context.md or from what the owner says. If there is no hint and there are several candidates, make asks which one. If there are none, it uses a plain style and says so.

Acceptance criteria

  • AC-pptx-studio-1 Creating a workspace with a name adds it to the list with an empty context.md; a duplicate name is refused with a message saying to pick another name
  • AC-pptx-studio-12 Deleting a workspace in the app after confirming removes its folder from disk and the workspace from the list
  • AC-pptx-studio-3 A file of any type up to the size limit uploads into a workspace and is listed with its name, type and size; downloading it returns the same bytes
  • AC-pptx-studio-4 A file over the size limit is refused with a message that names the limit, and nothing is stored
  • AC-pptx-studio-5 The resource panel previews md (rendered), code and plain text, images, video, PDF, csv/xlsx and pptx, and shows a file card for any other type
  • AC-pptx-studio-6 An uploaded .pptx or .potx, in a workspace or in the template library, shows slide thumbnails
  • AC-pptx-studio-13 A workspace, resource, template or version that is added, changed or removed in the folder from outside the app shows up in the open app within 5 seconds, without a reload
  • AC-pptx-studio-14 A readable versions/v<N>.pptx gets one PNG per slide and a done.json with the slide count in versions/v<N>-previews/
  • AC-pptx-studio-15 A versions/v<N>.pptx that is not a readable .pptx gets an error.txt that says what is wrong; the viewer shows it as failed and keeps the previous version as the current one
  • AC-pptx-studio-11 The workspace screen opens on the newest version with its slides, lets the owner switch versions, and Download .pptx returns a file that opens without repair errors; a version finished by an agent appears without a page reload
  • AC-pptx-studio-16 A request from another host or origin, or one whose name points outside the root folder, is refused and reads or writes nothing
  • AC-pptx-studio-17 The repository ships a suwpptx Claude Code plugin with the skills make, brief and template, and the plugin passes Claude Code's plugin validation

Risks and assumptions

Slide previews need a renderer. A browser cannot draw .pptx faithfully, so the server turns each version into images, usually with LibreOffice in headless mode. That is a large dependency, either on the machine or in the server's container with the root folder mounted. Its rendering differs slightly from PowerPoint's: fonts are replaced when they are missing, and some effects are lost.

Deck quality is Claude's, and the gate can't check it. Whether a deck fits the requirements and keeps the template's look depends on the skills and on Claude, not on server code. The acceptance criteria therefore cover only what the app does with the folder. The skills are judged by using them.

"Reuse the style" has limits. Building on the template file keeps its theme, fonts, slide masters and layouts exactly. A look made of hand-placed shapes on single slides, with no layout behind it, can only be imitated.

This leaves the template's stack. Without a database, Database/, Notes/, the database health check, the migrations, the PostgreSQL container and the tests that run against it all go. Server tests then work on a temporary folder. AGENTS.md and docs/architecture.md describe Notes and PostgreSQL as the pattern, so they change with this work.

The owner's machine has Python 3 with python-pptx for Claude to build decks with. The make skill checks for it and says how to install it when it is missing.
